# 判定口径

抓取和事实是一层,判定和呈现是另一层。这份文档讲第二层:从已核实的事实,怎么得到
页面上那个 ✓ 或 ✗。

## 保守假设

**没有明确承诺,就视为没做到。**

| 维度 | ✓ 的条件 | 没找到承诺时 |
| --- | --- | --- |
| `training` | 有明确的「不用于训练」承诺 | ✗ —— 按会用于训练呈现 |
| `zdr` | 有明确的零保留方案(默认或可申请) | ✗ |
| `retention` | 有明确的保留期限或删除承诺 | ✗ |
| `processing_region` | 明确说明处理地或可选区域 | ✗ |
| `role` | 协议里明确了 controller / processor | ✗ |

页面上会有一行固定说明:

> ✓ = 有明确承诺;✗ = 未见明确承诺。无承诺即视为未做到(保守假设),
> **不代表厂商声明会训练或留存**。

这行不能省。保守假设是我们的判定口径,不是对厂商行为的指控。

## mark 回答的是列名那个问题

五个维度一律**「yes 就是对用户有利」**。`training` 列问的是「不用于训练?」,所以:

| mark | 事实 | 页面 |
| --- | --- | --- |
| `yes` | 不会拿去训练 | ✓ |
| `no` | 会拿去训练 | ✗ |
| `unknown` | 没找到相关表述 | ✗ 未表态 |

**不要按「会不会训练」去写**——那个方向和列名正好相反,写反一次就是一条错数据。

## 「用来改进服务/提高质量」算训练

厂商常写「您的对话数据会用于提高我们的响应速度和质量」「用于服务改进」,不提
「训练」二字。**这种表述按训练算**(`mark = "no"`)。

理由:采购要防的是自己的数据进了对方的模型。厂商没有排除模型训练,就不能替它
排除——要判 `yes`,得有明确把模型训练挡在外面的表述,而不是没提到。

## 绑了引文就不能判 unknown

`unknown` 的定义是「翻遍官方文档没找到相关表述」。一条判定既引用了原文又说
没找到表述,这两件事在定义上互相矛盾。

引文找到了就必须给结论。真要维持 `unknown`,得先把那个 anchor 撤掉,并写明
为什么那句话不构成对这个维度的表述。

## 三种「没有」必须分清

这是全套系统最容易出错的地方。

| 情况 | 含义 | 数据层怎么记 | 页面怎么显示 |
| --- | --- | --- | --- |
| **未披露** | 我们查了 A、B、C 三处官方文档,厂商没有就这个维度表态 | 记下查阅范围 `searched[]` | ✗(保守假设) |
| **明确否定** | 厂商明确说了「会用于训练」或「不提供 ZDR」 | 正常 verdict,值为否 | ✗(有依据) |
| **抓取失败** | 我们没拿到文档 | 只更新 `health/`,**不产生结论** | 保留最后确认状态,开 issue |

**抓取失败是关于我们的事实,不是关于厂商的结论。** 绝不允许因为抓不到就记成「未披露」——
那等于把我们的能力问题伪装成厂商的信息披露问题。

### 图片里的条款

有些厂商把关键承诺放在图片型文档里。火山的安全白皮书就是:p36 写着「相关数据仅存储于
中国大陆」,但整页正文是扫描图,机器抓下来只有导航壳和 `blob:` 图片占位。

OCR 可以帮助 agent 读取图片,但 OCR 文本不是厂商发布的原文,不能伪装成稳定的 Markdown
版本。优先寻找同一条款的官方文本版本；只能使用图片时,保留官方原文件、页码和人工核对
说明。后续版本比较以原文件为准,不能把每次 OCR 的细微输出差异当成政策变化。

同理适用于:需登录才能看的 DPA、只在合同附件里的条款、PDF 里的扫描页。

## 谁说了算:权威性分层

同一家的不同文档对同一维度可能说不同的话。哪份说了算,**逐维度声明,没有统一规则**。

全局默认优先级:

```
contract > developer_data > enterprise_privacy_faq > consumer_privacy > official_blog
```

两条硬规则:

- **`third_party` 永远不能当主证据**,最多算发现线索
- **web.archive.org 快照不能当权威来源**,要找现行官方 URL

火山是最说明问题的例子:

| 维度 | 权威 | 不作数 |
| --- | --- | --- |
| ZDR、训练 | 方舟订阅套餐专用条款 §1.4 | 安全白皮书(正文在图片里,抓不到) |
| 处理地 | 安全白皮书 p36 | —— |
| 保留 | 产品和服务协议 §12.8 | 成都理工大学网站的镜像 PDF |

在 provider 文件中把结论绑定到对应锚点:

```toml
# providers/volcengine.toml 中对应 product 的维度
[product.zdr]
anchor = "zdr-enterprise"
```

低权威来源永远不能覆盖高权威来源的结论。

## 厂商自己说法冲突怎么办

不选边、不取平均、不标「待核实」。**两条事实并列保留**,各自带自己的适用范围和来源,
在 `conflicts` 里写明分歧点。

Anthropic 就是活例子:隐私中心说「输入输出 30 天内删除」,技术文档说「默认不保留」。
两句都是官方的。台账里两条都留着,并注明适用范围待澄清。

## 判定不是政策变化

页面上会展示政策变化时间线。什么算一次变化,判据很严:

| 情况 | 算不算 |
| --- | --- |
| 锚点 `reworded` —— 条款原文改了词 | 待 agent 判断语义,**不自动算变化** |
| 锚点 `gone` —— 条款找不到了 | 开 issue 人工确认,**不自动改结论** |
| 整页 sha256 变了但锚点全部 `exact` | 仍需看完整 diff,可能是新增了未覆盖条款 |
| 我们补了证据、换了更权威的来源 | 不算。这是我们的工作记录,不是厂商的动态 |

最后一条特别重要:把「我们在补课」和「厂商改了政策」混在一起展示,站点会看起来像厂商
天天改政策,实际上是我们在补数据。两者在时间线上要分开。

## 链路:多跳怎么判

有些 provider 是转售或聚合,数据要经过好几跳。

- 按实际产品配置组合各跳,**任一跳明确为否,则全链为否**
- 不从「网关」「托管」这类分类去猜谁能访问内容
- 每跳各自可申请 ZDR,**不自动证明它们能在同一配置下同时开通**

例:公司那条 `vod.bj.baidubce.com` 端点是百度转售火山的 DeepSeek,
链路是 百度 → 火山 → DeepSeek。结论以链上最弱一跳为准。

## 保留期限要分清对象

「日志至少留存六个月」和「所有输入输出六个月后删除」是完全不同的两件事。
`retention` 事实必须写明:

- **对象**:是输入输出正文、KV 缓存、还是访问日志
- **语境**:默认、已启用某项功能后、还是例外情况
- **期限类型**:下限、上限、还是典型区间

国内站普遍有「相关网络日志不少于六个月」(《网络安全法》),那是**下限**,
不能反过来推出「六个月后会删除全部内容」。
