# Data Flows & Privacy
Understand where code, prompts, model traffic, session history, and telemetry move in Factory Managed and Factory Private deployments.
**A local file read can still send file contents off the machine.** The model request can include the tool result, and cloud session sync can include it in the transcript. To exclude a new session from sync, tag it `local-only` at creation. Turning off Factory telemetry is a separate control; neither setting stops model requests.
For each destination, the data it receives, and the setting that controls it, see What leaves the machine during a Droid turn. The reference includes a runnable SDK example and a way to verify your policy with a disposable file.
High-security organizations need precise answers to **what data goes where, when, and under whose control**.
Factory's answer: **data boundaries are determined by the models, gateways, and deployment option you choose, and by your session sync and telemetry settings**. Droid is configurable to respect those boundaries. Even with Factory telemetry off and the session tagged `local-only`, a signed-in Droid still contacts Factory for identity, policy, feature flags, billing, and model provider and tool discovery, and sends a record of each MCP tool call; see Identity, policy, and tools.
## Overview: four main data flows
When you run Droid, there are four primary ways data can move:
1. **Code and files**: local reads and writes on your filesystem and git repositories.
2. **LLM traffic**: prompts and context sent to model providers or LLM gateways.
3. **Session history**: the session transcript, including tool results such as file contents, synced to Factory cloud unless cloud session sync is off or the session is tagged `local-only`.
4. **Telemetry**: Factory's own product logs, operational traces, and metrics, sent to Factory unless `telemetry.enabled` is `false`; and OpenTelemetry metrics to a collector you configure, with optional message content trace spans sent only to that collector.
How far each flow travels depends on whether you use **Factory Managed** or **Factory Private**.
| Deployment option | Data boundary |
| Factory Managed | Droid runs on laptops, CI, and Factory-managed compute, talking to Factory's control plane for orchestration and, optionally, analytics. LLM requests go to your chosen model providers or LLM gateways. |
| Factory Private | Factory runs the control plane by default, and Droid sandboxes run in your VPC through OpenCompute. Code execution and file access in those sandboxes stay in your VPC. LLM requests go to your chosen model providers or LLM gateways, and session storage follows your data settings. |

## Code and file access
Droid is a filesystem-native agent, and this holds in every deployment option:
- It reads your code, configuration, and test files **directly from the local filesystem** at the moment they're needed.
- It uses LLMs to analyze existing code and generate new code, then applies patches on disk, with git as the source of truth where available.
- It does **not** upload or index your codebase into a remote datastore, so Factory cloud holds no standing copy of your repository. The contents of files that Droid reads during a session are a different matter: they become part of the session transcript, which Droid syncs to Factory cloud unless cloud session sync is off or the session is tagged `local-only`.
- The **agent loop and runtime execute entirely on the machine** where Droid runs (developer workstation, CI runner, VM, or container), and **file reads and writes remain local** to that environment. File contents leave that environment inside the other flows: in LLM requests (prompts, context, and tool results) to the model endpoints you configure, in the synced session transcript, as arguments to MCP tools that Droid calls, and in message content trace spans if you send them to your collector.
- Hooks run locally inside that agent loop unless you configure them to call an external service. For Git operations run through Droid, Droid Shield scans changes being committed and the commits being pushed.
You control which files and directories Droid can see through standard OS permissions and your repository layout. See Agent Safety & Controls for additional file-level protections.
## LLM requests and model-specific guarantees
When Droid needs model output, it sends prompts and context to **your configured models and LLM gateways**.
By default, Droid can target **enterprise-grade endpoints** for providers like Azure OpenAI, AWS Bedrock, Google Vertex AI, OpenAI, Anthropic, and Gemini, using contracts that support zero data retention and enterprise privacy controls. In these configurations, Droid sends each request to Factory's model API, and Factory routes it to the provider's official API. We do not proxy this traffic through third-party services or store prompts and responses as part of routing them. Prompts and responses do reach Factory cloud separately, in the session transcript, while cloud session sync is on.
If you instead configure your own endpoints - LLM gateways, self-hosted models, or generic HTTP APIs - Droid sends the model request to that endpoint instead of Factory's model API, and the privacy guarantees for that request are entirely determined by those systems and your agreements with them; Factory does not add additional protections on top. Your own endpoint does not change the other flows: while cloud session sync is on, the transcript still syncs to Factory, and a signed-in Droid reports each custom-model request's usage to Factory's billing API, with token counts, the model name, and the gateway URL but not the prompt.

### How Droid interacts with models
- Org and project policies decide **which models and gateways are allowed**, and whether users can bring their own keys.
- In high-security settings, orgs commonly:
- Prefer the enterprise endpoints described above to get first-party zero-retention guarantees.
- Disable ad-hoc user-supplied keys and generic internet endpoints.
- Treat any LLM gateways or self-hosted models as in-scope security systems, subject to the same reviews and monitoring as other critical services.
See Enterprise Controls & Managed Settings for configuration details.
## Session history
While cloud session sync is on, Droid syncs each session's transcript to Factory so the session is available in the cloud: messages, tool inputs and results (which can include file contents), the title, the working directory, settings, and token totals. Choosing your own model or gateway does not change this.
To keep a new session out of Factory's cloud session history, tag it `local-only` when you create it. Setting `cloudSessionSync` to `false` stops content sync only where organization policy permits it: a user setting of `false` did not stop transcripts under an organization policy of `true`. The organization-wide switch is Session Contents Sync.
With content sync off, Droid can still register the session ID, host ID, tags, machine connection type, and timestamps. If an administrator enables Store Session Titles (`allowSessionTitleInMetadata`), registration also sends the session title. Leave Store Session Titles off to exclude titles, or create the session with `local-only` to skip registration and transcript sync. See Prompts, files, and session history for what each control stops.
## Telemetry and analytics
Telemetry is how you understand _what_ Droid is doing and _where_. Factory uses OpenTelemetry metrics for customer-owned observability and the hosted Analytics API for aggregated cloud analytics. Customers can optionally export message content as trace spans to their own collector. Set `telemetry.enabled: false` in managed settings to stop Factory product logs, operational traces, and metrics, and export to your own collector.
### OTEL as the source of truth
- Droid exports **OTLP metrics** by default to the endpoint pinned in org-managed settings (`telemetry.endpoint`) or configured per machine with `OTEL_TELEMETRY_ENDPOINT`. You can also opt in to message content trace spans, which are sent only to your collector.
- Droid does not send message-content spans through its built-in Factory telemetry exporter. If enabled, it writes them to the customer OTLP endpoint you configure. Droid does send Factory **operational spans** to `telemetry.factory.ai`, whether or not you configure a collector. They time startup, model calls, and tool calls, and record tool names and input and result sizes, but carry no prompts, responses, or file contents. `telemetry.enabled: false` stops them.
- Typical destinations include OTEL collectors feeding **Prometheus, Datadog, New Relic, Splunk**, and similar systems.
- Customer metrics export runs as a fan-out alongside Factory's own metrics export in connected deployments. Airgap builds export only to your collector, with no Factory-bound export built at all, and do not use Factory-hosted analytics.
- `telemetry.granularity: aggregate` removes `user.id` and `user.email` from usage metrics on both collectors. It does not anonymize all Factory telemetry: CLI 1.21.0 still attached `user.id` to Factory performance metrics. If those metrics must not leave the machine, set `telemetry.enabled: false` in managed settings. This does not disable identity or billing requests.
### Optional Factory cloud analytics
When Factory hosts the control plane, you can opt into Factory's own analytics dashboards, which may:
- Aggregate usage metrics to show adoption, model usage, and cost trends.
- Surface per-org and per-team insights for platform and leadership teams.
The dashboards are optional, but the usage metrics Droid sends to Factory are on by default and carry organization, user, and session IDs and the user's email. Org administrators turn that export off by setting `telemetry.enabled` to `false` in managed settings.
For telemetry setup and the hosted Analytics API, see Telemetry & Analytics; for the exported metric names and schema, see the Telemetry Data Reference; for how this data maps to audit and compliance workflows, see Compliance & Audit.

## Data retention and residency
### Factory-hosted components
Factory hosts the control plane in Factory Managed and, by default, in Factory Private. There, Factory may store:
- Authentication and administrative actions (for example, org configuration changes).
- Service health and debugging data, including the product logs, operational traces, and metrics that Droid sends unless `telemetry.enabled` is `false`.
- Session transcripts, while cloud session sync is on and the session is not tagged `local-only`. They include prompts, responses, and tool results such as file contents.
- Usage records for billing, including the usage reports for custom models.
Retention and residency for these logs are documented in the <a href="https://trust.factory.com">Trust Center</a> and can be tuned per customer engagement.
### Customer-hosted components
For the sandbox infrastructure you run in Factory Private:
<PropertyList>
<Property name='LLM traffic'>
When you route models through your own providers and gateways, they handle
the model requests and Factory does not see them. Factory still receives a
usage report for each custom-model request (token counts, model name, and
gateway URL), and the session transcript while cloud session sync is on.
</Property>
<Property name='Telemetry'>
What you export to your collector is stored in your observability stack;
retention is governed by your own policies. Factory's own logs, operational
traces, and metrics go to Factory unless `telemetry.enabled` is `false`.
</Property>
<Property name='Code, configuration, and secrets'>
File reads and writes happen in your VPC. File contents can leave it in
model requests, synced transcripts, MCP tool arguments, message-content
spans sent to your collector, or requests made by hooks and gateways.
Review the destination of each enabled flow.
</Property>
</PropertyList>
## Governance controls in practice
To make these guarantees enforceable rather than aspirational, Factory exposes **governance levers** at the org and project levels:
- Model and gateway allow/deny lists.
- Policies for whether user-supplied BYOK keys are allowed.
- Global and project-specific hooks for DLP, redaction, and approval workflows.
- OTEL endpoint configuration (including requiring collectors inside your network).
- Maximum autonomy level and other safety controls, especially in less-trusted environments.
These levers are implemented through Enterprise Controls & Managed Settings.
